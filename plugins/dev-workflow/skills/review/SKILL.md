# ローカルのレビュー

作業中のブランチの変更をレビューし、指摘を1つの一覧にまとめて、ユーザーが選んだものだけを反映する。一般的なバグの検出は組み込みの `/code-review` に任せ、このスキルが呼ぶサブエージェントは独自の観点だけを担当する。`/code-review` も同梱の観点 `code-review`（`builtin: code-review`）として観点の一覧に入り、ほかの観点と同じように止めたり条件を付けたりできる。今の変更に当てはまらない観点は、サブエージェントを起動する前に外す（設計書 §7）。

レビューと反映は手元だけの操作なので、実行の確認は取らない。ただし、どの指摘を反映するかは必ずユーザーに選んでもらい、選ばれていない指摘は反映しない（設計書 §8）。

スクリプト（JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/config.sh`：合わせた設定の出力（`review.max_rounds`：周回の上限。既定 3。最初のレビューを含む）。`review-perspectives.sh --auto` が、これを検査して `context.max_rounds` に出す。レビューのサブエージェントのモデル（`review.model`。既定 null で、セッションと同じモデル）は、`review-perspectives.sh --auto` が `config.sh` の値を検査した `context.model` を使う。`/code-review` に渡す effort の段階（`review.code_review_effort`。既定 null で、段階を渡さない）も同じく、検査した `context.code_review_effort` を使う
- `${CLAUDE_PLUGIN_ROOT}/scripts/review-perspectives.sh`：3つの層から観点ファイルを集め、今の変更に当てはまらない観点を外す（`--help` で観点ファイルの形式）

レビューを終えるときは、ユーザーが出した見落としの指摘や、今後も要らないとして却下した指摘を、観点に残すかを確かめる（手順9。設計書 §7）。観点を作るのは review-perspective-add スキルの手順に従う。

## 手順

### 1. 観点を決める

- コミットしていない変更があれば、先に commit スキルでコミットする（`/code-review` はコミットした変更だけを見るので、独自の観点と範囲を揃える）
- `review-perspectives.sh --auto` を実行する。基点・マージ先・Issue の番号・type はスクリプトが決めるので、自分で組み立てたり、引数を足したりしない

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/review-perspectives.sh" --auto
```

- 失敗したら（終了コードが 0 でない）、レビューを止め、標準エラーの1行のメッセージをそのまま伝える。絞り込まずに続けたり、自分で観点を選んだりしない
- 標準エラーの警告（`warn:`。Issue を読めない・マージ先を最新にできないなど）は、そのままユーザーに伝える
- 出力の `context` の `base` を基点、`issue` を Issue の番号（null なら Issue は無い）として、以下で使う
- 出力の `context` の `fallback` が null でなければ（PR のマージ先をそのまま使えず、`context` の `target` で判断した）、標準エラーの警告をそのまま伝え、どのマージ先でレビューしたか（`target`）を最後の結果にも書く
- 基点からの差分（`git diff <基点>`）が無ければ、レビューするものが無いと伝えて止める
- 出力の `context` の `max_rounds` が、周回の上限（設定の `review.max_rounds`。スクリプトが、1以上の整数かを検査する）
- 出力の `context` の `model` が、レビューに使うモデル（設定の `review.model`。スクリプトが、null か使える別名かを検査する）。null なら、手順3はセッションと同じモデルで動かす（Agent ツールに `model` を渡さない）
- 出力の `context` の `code_review_effort` が、`/code-review` に渡す effort の段階（設定の `review.code_review_effort`。スクリプトが、null か low・medium・high・xhigh・max のどれかを検査する）。null なら段階を付けない。付け方は、手順3の「`/code-review` に渡す引数」に従う

### 2. 観点を伝える

- 使う観点は `perspectives` にある観点だけ。`skipped`・`disabled`・`invalid` の観点は、手順3で起動しない
- `perspectives` が0件なら、レビューする観点が無いと伝えて止める
- `skipped` は、今の変更に当てはまらないので外した観点として、名前と理由（`reason`）をユーザーに伝える
- `invalid` があれば、ファイルと理由をユーザーに伝える（レビューは続ける）
- `disabled` は、止めている観点としてユーザーに伝える

### 3. 並行してレビューする

`perspectives` の観点ごとに、次のどちらかを、まとめて並行して実行する。

- **`builtin` が null の観点**：Agent ツールで、`subagent_type` を `dev-workflow:perspective-reviewer`（プラグインの agent。ファイルを編集するツールを持たない）にしたサブエージェントを1つずつ、同じメッセージの中で起動する。プロンプトには、観点ファイルのパス（`path`）・基点・マージ先（手順1の `context` の `target`）・Issue の番号（null なら「なし」）だけを書く（担当者への指示と返す JSON の形式は agent の定義にあるので、書き足さない）。手順1の `context` の `model` が null でなければ、Agent ツールの `model` にその値を渡す
- **`builtin` が `code-review` の観点**：組み込みの `/code-review`（Skill ツールの `code-review`）を、下の「`/code-review` に渡す引数」で決めた引数で実行する。使えない環境では、その旨を最後に伝えて、ほかの観点だけで進める。手順1の `context` の `model` が null でなければ、自分では実行せず、Agent ツールでサブエージェントを1つ（`model` にその値を渡して）、ほかの観点と同じメッセージの中で起動し、下の「`/code-review` を任せるサブエージェントへの指示」を、`<引数>` を下の「`/code-review` に渡す引数」で決めた値に置き換えて含める（Skill ツールで直接実行すると、セッションのモデルで動くため）

`context` の `model` を Agent ツールに渡しても、組織の制限や契約で使えないモデルなら、Claude Code が別のモデルに置き換えて動かす。置き換えを知らせる警告が出たら、そのままユーザーに伝える。

`/code-review` に渡す引数（1周目も再レビューも、自分で実行するときもサブエージェントに任せるときも、この決まりだけで決める）:

- `<対象>` は、1周目は今のブランチ名、再レビューは `<反映の前のコミットの sha>...HEAD`（その周の反映のコミットをすべて含む範囲。反映が1コミットでも複数でも同じ形。独自の観点に渡す基点と同じ sha なので、見る範囲が揃う。`/code-review` は、コミットの sha を1つだけ渡すとそのコミット1つだけを見るので、反映が複数のコミットになると、残りを見落とす）。ただし、再レビューで何も反映していないとき（手順8の「もう1周」で何も選ばれなかったとき）は、基点からの差分全体を見るので、今のブランチ名（1周目に基点の sha を渡すと、そのコミット1つだけをレビューしてしまう。反映したコミットがある再レビューにブランチ名を渡すと、前の周の指摘まで見てしまう）
- 手順1の `context` の `code_review_effort` が null でなければ、引数は `<段階> <対象>`（`<段階>` はその値。例：`high feat/12-add-thing`）。null なら `<対象>` だけ（段階を付けないので、`/code-review` が前に打った段階かセッションの effort を使う）

`/code-review` を任せるサブエージェントへの指示（`<引数>` は、上の「`/code-review` に渡す引数」で決めた値に置き換える。`<引数>` の文字のまま渡さない）:

```
Skill ツールの code-review を、引数 <引数> で実行する。ファイルは編集しない。
code-review が報告した指摘を、省かずにそのまま返す（場所・内容・直し方）。
Skill ツールを使えなければ、そのことだけを返す。
```

`dev-workflow:perspective-reviewer` へのプロンプト（`<基点>` には、手順1の `context` の `base`（基点）か、再レビューでは反映の前のコミットの sha を入れる）:

```
観点ファイル: <path>
基点: <基点>
マージ先: <context の target>
Issue: <Issue の番号、または なし>
```

`dev-workflow:perspective-reviewer` は、JSON のオブジェクト1つ（`findings`：指摘の配列、`notes`：確かめられなかったことと、観点ファイルが伝えるよう決めた文か null）で返す。返事は次のように読み、どの部分も捨てない（agent が形を守らないこともあるため）。

- 返事の中から、指摘の配列を読む。`findings` を持つ JSON のオブジェクトの `findings` を読む。オブジェクトに包まれていない配列（`[{"file": …}]`）は、どの項目も `file` と `summary` を持つときだけ、指摘の配列として読む。コードブロック（```json）で囲まれていたり、前置きの文が付いていたりしても読む。読んだ配列の各項目を、手順4の一覧に入れる指摘にする
- `notes` と、指摘として読まなかった部分（オブジェクトや配列の外にある文、指摘の形でない配列。コードブロックの囲みの記号は除く）は、その観点からの伝言にする
- 指摘の配列を読めない返事は、指摘にはせず、全文をその観点からの伝言にする（ほかの観点で続ける）

観点からの伝言は、観点の名前を添えて、言い換えずにそのまま伝える。伝えるのは、手順4（表の後。指摘が無いときは、その旨と一緒に）・手順5（質問の中）・手順7（結果）・手順8（上限の周の質問の中）。前の周の伝言は、手順8の上限の周の質問と、レビューを終えるとき（どの手順から手順9へ進むときも）に、今の周の伝言とまとめて伝える（同じ伝言は1回にする）。

### 4. 一覧にまとめる

このスキルは、反映の後に再レビューして周回する（手順8で決める）。今が何周目か（最初のレビューが1周目）と、前の周の指摘（場所と種類）を覚えておく。

- 観点の指摘（手順3の `findings`）と `/code-review` の指摘を1つの一覧にし、上から番号を付ける。各指摘には出どころ（観点の名前）を添える
- `/code-review` の指摘は、`perspectives` の `code-review` の観点ファイル（`path`）の本文に「## 指摘しないこと」の節があれば、その各項目と照らし、当たる指摘を一覧から外す。外した件数と、外した指摘の要約と当たった項目を、表の後に伝える（誤って外していないかをユーザーが確かめられるように）。同梱の `code-review.md` にはこの節が無いので、上位の層に置いたファイルに節があるときだけ外す。独自の観点の「指摘しないこと」は、サブエージェントが観点ファイルを読んで守るので、ここでは照らさない
- 同じ場所の同じ問題を複数が指摘していれば、1つにまとめて出どころを並べる
- 各指摘に「なぜ起きたか」を1行添え、その場所だけの誤り（局所）か、設計や前提の誤り（構造）かを分ける。最初の周から毎回行う。調べるのは指摘の周りのコードだけにし、サブエージェントは増やさない
- 構造の指摘には、その場所を直す案と並べて、根本を直す案（その仕組み自体が要らないかも含めて）を添える
- 各指摘に「水平展開の要否」も判定する。局所の指摘でも、同じ書き方・同じ前提で書かれた場所をリポジトリで検索（`git grep` など）し、同じ誤りが残っていれば、その場所も同じ一覧に加える（指摘の「直し方」には、検索した結果の場所を並べる）。残っていなければ「水平展開は不要（検索した語と、見つからなかったこと）」と添える。最初の周から毎回行い、調べるのは検索で見つかった場所だけにする（サブエージェントは増やさない）。検索で見つかった場所は、差分の外でも例外として一覧に加える（このスキルの範囲は基点からの差分だが、水平展開の場所だけは、その指摘と同じ誤りに限って差分の外も対象にする）
- 前の周と同じ場所、または同じ種類の問題が、これまでの周を合わせて2回以上出ている指摘には「繰り返し」と印を付ける（手順8）。照合は、同じファイルで、同じ観点か同じ種類の問題かどうかで行い、行番号は使わない（反映で行がずれるため）
- 並べ方は、壊れる・誤る問題を先に、書き方の問題を後にする
- 一覧を表で見せる（番号・出どころ・ファイルと行・要約・原因（局所／構造）・水平展開（要る場所／不要）・直し方。繰り返しの指摘は印を付ける。構造の指摘は、根本を直す案も添える）
- 指摘が1つも無ければ、その旨と、レビューした観点の一覧・外した観点とその理由・観点からの伝言（手順3）を伝え、手順9へ進む
- 表の後に、外した観点（`skipped`）の名前と理由と、観点からの伝言（手順3）を添える

### 5. 反映するものを選んでもらう

AskUserQuestion の複数選択（`multiSelect: true`）で、反映する指摘を選んでもらう。

- 1つの質問に選択肢は4つまでなので、4件ずつ質問を分ける（1回で4問・16件まで）。17件以上あるときは、表の番号で答えてもらう（「Other」に番号を書いてもらう）。このときは、選択肢に入らない指摘も番号で選べるように、表（番号・要約・ファイルと行）を質問の文に入れる
- 選択肢のラベルは番号と短い要約、説明には出どころ・ファイルと行・原因（局所か構造か）・水平展開の場所（あれば。反映すると、その場所も直されると分かるように）・直し方（構造なら根本を直す案も）を書く。繰り返しの指摘には、ラベルに「繰り返し」と書く。手順4の表と、観点からの伝言（手順3）は、質問の中にも入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。複数選択の質問では preview を使えないので、表を見なくても選べるように、説明だけで指摘の中身が分かるように書く
- 何も選ばれなければ、何も変えない。上限の周なら手順8の確認へ進み、それ以外は手順9へ進む

### 6. 反映する

選ばれた指摘だけを直す。選ばれていない指摘に関わる変更はしない。

- 指摘に水平展開の場所が付いていれば、その場所も同じ方法で直す（選ばれた指摘の一部として扱う）。直した後、同じ検索をもう一度実行して、同じ誤りが残っていないことを確かめる
- 直したら、テストとチェックを実行して通ることを確かめる。実行するコマンドは、`${CLAUDE_PLUGIN_ROOT}/scripts/checks-commands.sh` を実行し、`--help` の「決め方」（設定 `checks.commands` → リポジトリの手がかりから推測 → ユーザーに聞く）に従って、実行するコマンドを決める。出力の `action` に従う：`run` は `commands` を絞らず全部実行し、`confirm` は実行する前にコマンドを見せて確認を取り（確認が取れるまで実行しない）、取れたら全部実行し、`none` は何も実行せず、`infer` は手がかりから推測する。ユーザーに聞いたときは、答えを `checks-commands.sh --save --scope <local・team> --command <コマンド>`（実行するものが無いなら `--none`）で設定に保存するかも聞く。出力の `saved.warning` があれば、そのままユーザーに伝える。
- 直した内容は、論理的な区切りごとに commit スキルでコミットする
- 直し方が複数ありえて決められないときは、ユーザーに聞く
- 「繰り返し」の指摘は、直す前に、これまでの修正が表面的でなかったか（同じ原因から出た症状を、その場所ごとに直していなかったか）を確かめ、根本の原因とそれを直す案を必ず示す。その場所だけを直す案で済ませない。根本を直す案が大きな変更になるなら、どちらで直すかをユーザーに聞く

### 7. 結果を伝える

反映した指摘と、そのコミット（短い sha と1行目）、反映しなかった指摘の番号を伝える。外した観点（`skipped`）があれば、その名前と理由も改めて伝える。これまでの周の観点からの伝言（手順3）があれば、それも改めて伝える。

### 8. 再レビューするか決める

周回の上限は、設定の `review.max_rounds`（最初のレビューを含む。既定 3）。手順1の `context` の `max_rounds` を使う。今の周の番号は、最初のレビューが1周目。次の順に決める（周回を終える出口はここだけで、上から当てはまったものに従う）。下で「終える」ときは、手順9へ進む。

1. **今の周が上限に達していて、その周の一覧に指摘があった**（反映したかどうか、反映で振る舞いが変わったかどうかは問わない。何も選ばれなかったときも含む）：自動では回さず、AskUserQuestion で「もう1周レビューする」「ここで終える」を選んでもらう。選択肢の説明には、一覧の指摘（番号と要約）と、選ぶと何が起きるか（再レビューを1周する／ここまでの反映で終える）を書く。これまでの周の観点からの伝言（手順3）があれば、それも質問の文に入れる。「もう1周」なら下の再レビューを行う。続けるなら、その周でも指摘が出るたびに同じように聞く（4周目以降も回せる）
2. **反映したコミットが無い、または、反映で振る舞いが変わっていない**（言い換え・コメント・文章の整えだけ）：再レビューは要らないので終える
3. **それ以外**（上限より前の周で、振る舞いが変わった）：自動で再レビューする

上限で終えた後も、ユーザーの「もう一度レビューして」で、いつでも手順1から実行できる（周の数は数え直す）。

再レビューは、今の周で反映したコミットの差分だけを見る（1の「もう1周」で何も反映していなければ、基点からの差分全体）。

- 手順1の `review-perspectives.sh --auto` をもう一度実行し、当てはまる観点を決め直す（失敗したときの扱いも手順1と同じ）
- `/code-review`（Skill ツールの `code-review`）には、手順3の「`/code-review` に渡す引数」で決めた引数（再レビューの `<対象>`）を渡す。`context` の `model` が null でなければ、手順3のとおりサブエージェントに任せる。当てはまる独自の観点は、手順3のとおり `dev-workflow:perspective-reviewer` で起動し、基点には反映の前のコミットの sha を渡す（その周の反映のコミットの差分だけを見るため。`/code-review` の範囲 `<反映の前のコミットの sha>...HEAD` と同じ範囲になる）
- 手順4からの流れで、新しい指摘を一覧にする。前の周の指摘と同じ場所や同じ種類のものには、手順4のとおり「繰り返し」の印を付ける
- 新しい指摘が無ければ、再レビューでも指摘が無かったことを、手順4の「指摘が1つも無ければ」のとおり伝えて終える

### 9. 観点に残すか確かめる

手順4・5・8でレビューを終えるとき（周回を終えたときを含む）に行う。手順1・2で止まったときは行わない。この会話でのユーザーの発言から、次の2つを探す。どちらも無ければ、何も聞かずに終える。

- **見落とし**：レビューの一覧に無かった、変更への指摘をユーザーが出した（選択の「Other」に書いた、一覧を見て別の問題を挙げた、など）
- **今後も要らない指摘**：反映しなかった指摘に、ユーザーが理由を述べ、その理由がその場限りでなく、今後も同じ種類の指摘を要らないとするもの（例：「この書き方はこのリポジトリでは許容」）。理由が述べられていなければ対象にしない（反映しなかっただけでは、今後も要らないかは分からない）

次は対象にしない。

- 一般的なバグ（`/code-review` の範囲）。観点を足しても、観点の外のこととしてサブエージェントは指摘しない
- その場限りの好みや、この変更だけの事情

見つけたものを、1つずつ AskUserQuestion の単一選択の質問にする（1回で4問まで。5つ以上あれば分けて聞く）。どれも、選ばれたものだけを変え、自動では変えない。「何も変えない」が選ばれたら、何も作らず、何も直さない。各選択肢の preview には、作るファイルの中身か、直した後の本文（足す行が分かるように）を入れる（設計書 §8。別の端末から使うと、質問の直前の文章が見えないことがある）。

**見落としのとき**

1. `review-perspectives.sh`（引数なし）で今ある観点を読み、同じことを確かめるはずだった観点があれば、その観点ファイルを読む。その観点の書き方が足りなかった（確かめ方が書かれていない・範囲が狭い）のか、どの観点も見ていないのかを見分ける
2. 選択肢は「既にある観点 <名前> を直す」（見分けた結果、当てはまる観点があるときだけ）・「新しい観点 <名前> として残す」・「観点に残さない（何も変えない）」。見分けた結果に合うほうを先に置く。新しい観点の中身は、review-perspective-add の手順3のとおりに書く
3. 新しい観点なら、review-perspective-add の手順2・4〜6に従って作る（置く層はユーザーが選ぶ。聞き取りの手順1は、指摘の内容で済ませる）
4. 既にある観点を直すなら、そのファイルがユーザーかリポジトリの層にあれば、そのファイルを直接直す（リポジトリの層は、今のタスクのワークツリーで直す）。同梱の層にあれば、プラグインのファイルは直さず、直した中身で同じ名前の観点を上位の層に作る（review-perspective-add の手順4〜6。元のファイルと同じ title と実行する条件で、`--override` を付ける）

**今後も要らない指摘のとき**

指摘の出どころの観点ファイルに、外す決まりを1項目足す。項目には、何を外すか（ファイル・書き方などの対象）と理由を、ほかの変更でも当たるかを判断できるように書く。広すぎて、本当の問題まで外れないようにする。「〜を指摘しない」だけの観点は新しく作らない（観点は別のサブエージェントで動くので、ほかの観点の指摘を止められない）。

1. 足す先を決める
   - 独自の観点：その観点ファイルの「指摘しないこと」に足す（無ければ、本文の最後に「次は指摘しない。」として足す）
   - `/code-review`：使った `code-review` の観点ファイル（手順1の `perspectives` の `path`）の「## 指摘しないこと」の節に足す（無ければ節を作る）
   - 複数の観点が出どころなら、それぞれに足す
2. 選択肢は「今後は指摘しない（<ファイル> に足す）」・「今回だけにする（何も変えない）」。足す項目とファイルを、説明と preview に書く
3. 足すファイルがユーザーかリポジトリの層にあれば、そのファイルを直接直す（リポジトリの層は、今のタスクのワークツリーで直す）。同梱の層にあれば、プラグインのファイルは直さず、足した中身で同じ名前の観点を上位の層に作る（review-perspective-add の手順4〜6。置く層はユーザーが選ぶ。元のファイルと同じ title と実行する条件で、`--override` を付ける。`code-review` なら `--builtin code-review` を付け、本文は「## 指摘しないこと」の節だけにする）

最後に、作ったり直したりしたファイルのパスと変えた中身を伝える。リポジトリの層のファイルは、今のタスクのブランチで commit スキルでコミットし、そのタスクの PR に含める（観点のためだけに別の Issue は立てない。設計書 §7）。次のレビューから使われることも伝える。
