# gh-pr-check の見回りは、pr-watch.sh を呼ぶシェルのループを背景で動かし、対応が要る状態になったときだけ Claude に戻す

## 背景と課題

PR を出した後、CI とレビューを待つ間、手で何度も確認する必要がある。gh-pr-check に見回りを足し、手元のセッションで人が待つときに、マージできる状態になるまで PR を一定の間隔で見回したい（#340）。判定は `pr-watch.sh` の `action`（`idle`・`wait`・`act`・`conflict`）を使い、見回りを終える条件は [ADR 000285](000285-unattended-pr-repair-scope.md) に従う。CI で無人で直す見回りは ADR 000285 が決めているので、ここで決めるのは、人が手元のセッションで待つ見回りの方式だけである。

セッションの中で見回りを動かす手段は複数あり（`/loop`・`ScheduleWakeup`・`Monitor`・背景のシェル）、使用量・書き込み・会話の占有が手段によって違う。どれを使うか。

## 判断の決め手

* 対応が要らない回（`wait`）に、プランの使用量を消費しないこと
* 対応を始めるまで、GitHub にも手元にも何も書き込まないこと（マージは人が行う。ADR 000267）
* 待っている間も、会話を占有しないこと
* 特定の実行環境の機能に頼らず、使えない環境が少ないこと
* 判定は `pr-watch.sh` の1か所に置き、見回りが判定を重ねて持たないこと

## 検討した案

* シェルのループを背景で動かす
* `/loop`（`ScheduleWakeup`）で、毎回 Claude が確認する
* `Monitor` で、背景のループの出力を監視する

## 判断の結果

選んだ案：「シェルのループを背景で動かす」。理由は、待っている間は Claude を動かさないので、決め手の「対応が要らない回に使用量を消費しない」を満たす唯一の案だから。

見回りは次のように動く。

* gh-pr-check に見回りの指定（間隔と上限）を足す。既定は、間隔 60 秒、上限 60 分とする。引数で、間隔（1 以上 86400 秒以下）と上限（回数、または 1 以上 10080 分以下の分）を変えられる。間隔と分に上限を置くのは、積が bash の整数の範囲を超えないようにするため。設定のキーは足さない
* ループは、指定の間隔で `pr-watch.sh` を呼ぶシェルのスクリプトとし、背景で実行する。`action` が `wait` の間は続け、`wait` 以外になるか、上限に達したら、最後の出力を残して終了する。終了で Claude が呼び戻される
* Claude は、呼び戻されたときの `action` で分ける。`idle`（マージできる状態）は止まって報告する。`act` は止まって、対応するかを聞く（対応するなら、gh-pr-check の確認から対応の手順に進む）。`conflict` は止まって、`/dev-workflow:branch-update` を案内する。上限に達したときは、状態を報告して止まる
* ループと、呼び戻された後の報告までは、何も書き込まない。書き込むのは、人が対応すると答えた後の、gh-pr-check の既存の手順（確認を取ってから push と返信）だけである
* ループの終了を待つ間、会話は占有されない

### 結果として起きること

* 良い点：待っている間は Claude を動かさないので、使用量を消費しない。対応が要る状態になったときの1回分だけ消費する
* 良い点：判定は `pr-watch.sh` のまま使うので、見回りと手動の確認で判定が食い違わない
* 良い点：シェルと背景実行だけで動くので、`Monitor` などの特定のツールに頼らない
* 悪い点：ループ用のスクリプトが1つ増え、bats でテストする対象が増える
* 悪い点：セッションを閉じるとループも止まる。待ち続けたいときは、無人の見回り（ADR 000285）を使う
* 悪い点：背景実行の仕組みが無い実行環境（`claude -p` など）では、見回りを使えない

### 確認

ループ用のスクリプトの bats のテストで、`wait` の間は続けること、`wait` 以外で終了すること、上限（回数・時間）で終了すること、何も書き込まないこと（`gh` の書き込みの呼び出しが無いこと）を確かめる。gh-pr-check の SKILL.md のテストで、`action` ごとの分け方（止まって報告・対応を聞く・branch-update の案内・上限の報告）が書かれていることを確かめる。

## 各案の長所と短所

### シェルのループを背景で動かす

`pr-watch.sh` を間隔ごとに呼ぶシェルを背景で実行し、`wait` 以外か上限で終了させる。

* 良い点：待つ間に Claude を動かさず、使用量を消費しない
* 良い点：会話を占有しない
* 良い点：既存の `pr-watch.sh` の判定をそのまま使える
* 悪い点：スクリプトが1つ増え、セッションを閉じると止まる

### `/loop`（`ScheduleWakeup`）で、毎回 Claude が確認する

間隔ごとに Claude が起き、`pr-watch.sh` を呼んで、`wait` なら次の回を予約する。

* 良い点：新しいスクリプトが要らない
* 悪い点：対応が要らない回ごとに、Claude の1ターン分の使用量を消費する。決め手の「対応が要らない回に使用量を消費しない」に反する
* 悪い点：1回ごとに文脈が積まれ、待つ時間が長いほど会話が重くなる

### `Monitor` で、背景のループの出力を監視する

背景のループの出力を `Monitor` で監視し、変化があったときに通知を受ける。

* 良い点：待つ間の使用量は小さい
* 悪い点：`Monitor` が使えない実行環境では動かない
* 悪い点：ループ用のスクリプトは結局必要で、背景のシェルが終了で呼び戻す仕組みに対して得るものが少ない

## 補足

* 見回りを終える条件は [ADR 000285](000285-unattended-pr-repair-scope.md) の「見回りを終える条件」に従い、判定は `pr-watch.sh`（#308・#340）が行う。この ADR は、その判定を手元のセッションでどう繰り返すかだけを決める。無人の見回りの方式は変えない
* 同じ head_sha で `act` を返し続けない仕組みは、[別の ADR](000340-pr-watch-stop-on-repeated-attempts.md) で決めた
