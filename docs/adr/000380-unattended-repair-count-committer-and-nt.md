# 無人の push の回数は、head が進んだ先のコミットの committer が無人の実行のものだけを数え、止めるパスは NTFS で同じ名前になる別名も含める

## 背景と課題

[ADR 000339](000339-unattended-repair-push-scope-and-run-cou.md) は、無人の push の回数を「PR の head が `repair-run` の `head` の sha から進んだ回」だけを数えると決め、止めるパスを `.github`・`.claude` とその以下にした。その後の自動のレビューで、次の穴が見つかった（#348・#356）。

* 無人の push が失敗しても、ほかの bot（依存関係の更新など）の push で PR の head が進むことがある。このとき、push していない `repair-run` も「head が進んだ」と数えられ、`repair.max_pushes_per_pr` の上限に早く達する。
* `repair-push-check.sh` は、パスの大文字と小文字を区別せずに照らす。しかし NTFS（Windows）では、末尾の点・空白（`.claude.`・`.github `）や、8.3 形式の短い名前（`.claude` は `CLAUDE~1`、`.github` は `GITHUB~1`）も、`.claude`・`.github` と同じ名前として読まれる。これらを含むパスは、検査をすり抜ける。

head が進んだ原因が無人の実行の push かどうかを、どう見分けるか。NTFS の別名を、どこまで止めるか。

## 判断の決め手

* push していない回で上限に達して、直せる PR が止まらないこと
* 見分け方が、コメントの追記のような後からの操作の成否に頼らないこと
* 判断できないときは、上限を超えない側（数える側・止める側）に倒すこと
* 無人の実行が、CI・権限・Claude の設定を変えて main に入る道を残さないこと（ADR 000285）

## 検討した案

push の回数の数え方

* ADR 000339 のまま、head が進んだ回をすべて数える
* PR のコミットの一覧から、`head` の sha を親に持つコミット（進んだ先）を探し、その committer が無人の実行のものの回だけを数える
* 無人の push の後にだけコメントを付ける（push の後に付ける）

NTFS の別名

* 止めない（大文字と小文字の違いまで）
* 各階層の名前から末尾の点・空白を除き、8.3 形式の短い名前（`claude~<数字>`・`github~<数字>`）を `.claude`・`.github` に直してから照らす

## 判断の結果

選んだ案：数え方は「進んだ先のコミットの committer が無人の実行のものだけを数える」、NTFS の別名は「正規化してから照らす」。

* `repair-run-count.sh` に `--commits FILE`（`gh api --paginate --slurp 'repos/{owner}/{repo}/pulls/<PR番号>/commits?per_page=100'` の出力）を足す。指定すると、head が進んだ回のうち、`head` の sha を親に持つコミットの committer のログインが `--logins`（`repair.reply_logins`。大文字小文字と末尾の `[bot]` を除いて比べる）のものだけを、`head` の値ごとに1回と数える。ほかの committer だけの回は数えず、出力の `other_pushed` に数を出す。
* 進んだ先のコミットが一覧に無いとき、committer のログインが読めないとき、`--logins` が空のときは、数える側に倒す（ADR 000285 の「少なく数えて上限を超えない」と同じ向き）。`--commits` を省くと、今までどおり head が進んだ回をすべて数える。
* `repair-push-check.sh` は、パスの各階層について、末尾の点と空白を除き、8.3 形式の短い名前を `.claude`・`.github` に直してから、今までの規則で照らす。名前が似ているだけのパス（`claude~x`・`a.claude.`）と、入れ子の `.github` の別名は止めない。止めるパスの一覧の正本は、今までどおり `repair-push-check.sh --help`。

### 結果として起きること

* 良い点：ほかの bot の push で head が進んでも、push していない回が上限に数えられない。
* 良い点：NTFS の別名で、`.claude`・`.github` 以下の変更を無人で push できなくなる。
* 悪い点：見回りが PR のコミットの一覧も読む必要がある（1回の API 呼び出しが増える）。
* 悪い点：PR のコミットが 250 を超えると一覧が欠け、進んだ先が見つからない回は数える側に倒れる。
* 悪い点：`claude~1` のように、実在する別のファイル名も止めることがある（人が直す）。

### 確認

* `tests/repair-run-count.bats` で、他の bot の push で head が進んだ回を数えないこと、無人の実行の committer の回は数えること、進んだ先が一覧に無い・committer が読めないときは数えること、`--commits` が無いときは今までどおりなこと、不正な入力で終了コード 64 になることを確かめる。
* `tests/repair-push-check.bats` で、末尾の点・空白、8.3 形式の短い名前を含むパスが止まること、似ているだけのパスは止まらないことを確かめる。
* `tests/skills.bats` で、branch-update の無人の手順に `--commits` の渡し方が書かれていることを確かめる。

## 各案の長所と短所

### head が進んだ回をすべて数える（ADR 000339 のまま）

* 良い点：入力がコメントと head だけで済む。
* 悪い点：ほかの bot の push で、push していない回も数えられる。

### 進んだ先のコミットの committer で絞る

* 良い点：コメントの追記や後からの操作に頼らず、PR の履歴から見分けられる。
* 悪い点：PR のコミットの一覧が要る。committer のログインが GitHub のアカウントに結び付かないコミットは見分けられない（数える側に倒す）。

### push の後にコメントを付ける

* 良い点：push した回だけにコメントがある。
* 悪い点：push の後、コメントの前に落ちると、push した回が数えられず、上限が効かない（ADR 000339 で退けた案）。

### NTFS の別名を止めない

* 良い点：実装が単純。
* 悪い点：Windows で `.claude.` や `CLAUDE~1` として読まれ、無人の push が Claude の設定や CI を変えられる。

### 正規化してから照らす

* 良い点：並べ漏らしが少なく、今までの規則をそのまま使える。
* 悪い点：`claude~1` のような実在の別名のファイルも止まる。

## 補足

* 出典：Issue #380（#348・#356 をまとめたもの）。
* [ADR 000339](000339-unattended-repair-push-scope-and-run-cou.md) を一部だけ変える。変えるのは、「push の回数の数え方」（head が進んだ回 → 進んだ先のコミットの committer が無人の実行のものの回）と、「止めるパス」のパスの照らし方（NTFS で同じ名前になる別名も同じ名前として扱う）。それ以外の判断は変えない。ADR 000339 は書き換えない。
