# Issue から PR まで自動で進める

Issue を指定されたら、ユーザーを介さずに、着手から PR の作成まで進める。このセッション（指示役）が、今のスキルの手順をたどりながら、各スキルが AskUserQuestion で取る確認に代わりに答える。実装・テスト・コミットは作業役のサブエージェントに任せ、レビューは `/dev-workflow:review` を使う（設計書 §8「Issue から PR まで自動で進める（task-auto）」）。

確認を取る範囲（ADR 000064）を、設定 `auto.enabled` を true にしたリポジトリでだけ、指示役の判断に置き換える（ADR 000267）。無効なら、何もせずに止まる。今のスキルの振る舞い（確認を取る）は変えない。

決まり:

- **AskUserQuestion は使わない**。下の「確認の代わりに決めること」に無い確認や、決めきれない場面に当たったら、聞かずに「止まる」の手順で止まる
- PR は draft にせず、レビューできる状態（オープン）で出す（`pr-create.sh --no-draft` を付ける。設定 `pr.draft` が true でも下書きにしないため。PR の自動レビューの多くは draft をレビューしないため。ADR 000280）。既にある下書きの PR を使うときは、下書きのまま残し、`gh pr ready` は実行しない（ready にするかは人が決める。手順6）。マージはしない（`allow_ai_merge` にかかわらず）。Issue を閉じない。強制 push をしない
- GitHub に書き込むのは、着手（割り当てと列の移動）・範囲外の指摘の起票・push と PR の作成・手順7で後から起票した Issue を、task-auto が自分で作った PR に付けるコメント・止まるときのコメントと列の移動だけ。ほかの Issue や PR を書き換えない。PR の本文は、作るとき以外は直さない
- 代わりに決めたことは、すべて覚えておき、PR の本文の「自動で決めたこと」の節（止まったときは Issue のコメント）に書く
- ワークツリーとコミットは、止まったときも残す（人が続きから進められるように）

スクリプト（どれも JSON を出力する）:

- `${CLAUDE_PLUGIN_ROOT}/scripts/auto-check.sh`：始める前に、設定と Issue から、進めるか・止まるか（`action`）と、前の作業のブランチを使い回すか（`resume`）を決める。何も変えない（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/merge-target.sh`：今のブランチのマージ先（開いた PR があればそのマージ先、無ければ `base_branch`）を決め、origin から取得する（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/auto-findings.sh`：範囲外とした指摘の記録（JSON のファイル）を検査し、全件に起票した番号か起票しなかった理由があることと、件数がレビューの一覧から数え直した数と合うことを確かめる。PR を作る前に使う。何も変えない（`--help` で使い方）
- `${CLAUDE_PLUGIN_ROOT}/scripts/auto-hold.sh`：止まる理由とそれまでの判断を Issue にコメントし、保留の列に移す（`--help` で使い方）
- 着手・コミット・レビュー・PR の作成は、それぞれのスキルのスクリプト（`task-start.sh`・`next-tasks.sh`・`commit.sh`・`review-perspectives.sh`・`adr-list.sh`・`pr-create.sh`・`issue-create.sh`）を、そのスキルの手順どおりに使う

## 確認の代わりに決めること

今のスキルの確認に当たったら、次のとおりに答える。この表に無い確認は、止まる。

| スキル・場面 | 今のスキルの確認 | task-auto の答え |
|---|---|---|
| task-start 手順4 | ワークツリーを作るか | 作る。「変更するファイル・領域」が「- なし」（ファイルを変えないタスク）なら、PR を出せないので止まる |
| task-start 手順4 | 着手中の Issue と変えるファイルが重なる（`conflict`）・分からない（`unknown`） | 着手する。重なる Issue とパス（分からないときはその理由）を「自動で決めたこと」に書く |
| task-start 手順5 | ブランチ名の短い説明 | 前の作業のブランチ（`auto-check.sh` の `resume`）があれば、短い説明は決めずに、そのブランチを名前のまま使う。無ければ Issue のタイトルから英語で決める。どちらも「自動で決めたこと」に書く |
| task-start 手順1 | type ラベルを直すか | 直さない。`auto-check.sh` が止める |
| commit 手順2 | どの変更を含めるか迷う | 作業役が Issue の範囲で決め、決めたことを報告する。秘密の情報・生成物は含めない |
| review 手順5 | 反映する指摘 | Issue の範囲内の指摘はすべて反映する。範囲外の指摘と前からある不具合は反映せず、起票する（手順5） |
| review 手順6 | 直し方が決められない | Issue と、周りのコードの書き方に合う方を選び、「自動で決めたこと」に書く。どちらとも決められなければ止まる |
| review 手順6 | 「繰り返し」の指摘の、根本を直す案が大きい | 根本を直す案が Issue の範囲内なら、それで直す。範囲を超えるなら止まる |
| review 手順8 | 上限の周でも指摘が出たら、もう1周するか | もう1周しない。範囲内の指摘を反映してコミットし、テストとチェックが通れば、止まらずに PR の作成（手順6）へ進む。最後の反映がレビューされていないことを「自動で決めたこと」に書く |
| review 手順9 | 観点に残すか | 聞かない（ユーザーの発言が無いので、対象が無い） |
| task-create 手順2・3 | 重複の扱い・起票の確認・Story Point | 重複があれば起票しない。無ければ起票し、Story Point は空欄にする（手順5） |
| task-create 手順6 | 起票した後に着手するか | 聞かず、着手しない（起票だけで終える。範囲外の指摘の Issue は人が着手を決める） |
| pr-create 手順2・5 | ADR を作るか（`proposal` が `pending`・`judge` で判断がある） | 止まる |
| pr-create 手順5 | PR の内容・チェックする項目 | task-auto の手順6のとおりに決めて、確認せずに作る |
| pr-create 手順5 | 既にある PR の本文を直すか | 直さない。既にある PR に push するだけにし、書いた本文を出さなかったことを報告する。下書きなら下書きのまま残し（`gh pr ready` は実行しない）、人に ready にするよう伝える（手順6・7） |
| どの場面でも | 上に無い確認・判断できない問い | 止まる |

## 止まる

次のどれかに当たったら、それ以上進めずに止まる。

- `auto-check.sh` の `action` が `hold`（breaking ラベル・type ラベルが1つでない・「やること」や「完了条件」が無い・前の作業のブランチを1つに決められない）
- Issue があいまい（task-auto の手順1）
- テストや lint が、`auto.max_fix_attempts` 回直しても通らない（task-auto の手順3）
- 差分に ADR にすべき判断がある、または Issue の ADR の項目が残っているのに ADR が無い（task-auto の手順6）
- 作業役が、Issue と周りのコードから決められない問いを返した（task-auto の手順3）
- スクリプトが止まり、手順に直し方が書かれていない（push できない・PR を作れないなど）
- 上の「確認の代わりに決めること」に無い確認に当たった

止まるときは、次の順に行う。

1. 作業役に任せた作業が途中なら、コミットしていない変更を作業役にコミットさせる（テストが通っていなくても、`wip` と分かる要約で残す。commit スキルの規約に沿う）。ワークツリーとブランチは消さない。push もしない
2. コメントの本文を一時ファイルに書く。言語は設定の `language` に従う。次を見出しごとに書く
   - **止まった理由**：当たった条件と、その中身（落ちたテストの名前とエラーの要点、残った指摘、あいまいな点と考えられる解釈など）
   - **それまでの判断**：「自動で決めたこと」に覚えた内容（ブランチ名・重なり・反映した指摘と反映しなかった指摘・起票した Issue など）
   - **残したもの**：ブランチ名・ワークツリーの場所・コミット（短い sha と1行目）。着手する前に止まったときは「着手していない」
   - **続けるには**：人が決めること・直すこと（例：「完了条件を書き足してから、Issue を Todo に戻して、もう一度 task-auto を実行する」）
3. `auto-hold.sh --issue <番号> --run-id <実行の id> --reason-file <ファイル>` を実行する（実行の id は、task-auto の手順1「進めるかを決める」で決めたもの。この節の1ではない）。Issue にコメントが付き、保留の列に移る。失敗したら、標準エラーの1行のメッセージをそのまま伝える（同じ実行の id でもう一度実行すれば、コメントは付け直さずに続きから進む）
4. ユーザーに、止まった理由・Issue の URL・残したもの（ブランチとワークツリー）を伝える

`auto-check.sh` の `action` が `disabled`・`no_hold`・`not_startable` のとき（task-auto の手順1）は、この手順では止まらない（何も書き込まない）。

## 手順

### 1. 進めるかを決める

引数があれば Issue の番号として使う（`12` でも `#12` でもよい）。引数が無ければ、依頼の文章から番号を読む。それでも分からなければ、何もせずに、番号を付けて頼み直すよう伝えて終える（聞かない）。

実行の id を1つ決めて覚えておく（`date -u +%Y%m%dT%H%M%S` の出力に `-` と4桁の乱数を付けたもの。例：`20261008T101500-4821`）。止まるときに `auto-hold.sh --run-id` に渡す（同じ実行の再試行と、別の実行で新しく止まったことを見分けるため）。

`auto-check.sh --issue <番号>` を実行し、`action` に従う。

- `disabled`：何もせずに終える。設定 `auto.enabled` が true でないので自動では進めないことと、使うなら `.claude/dev-workflow/config.json`（自分だけなら `config.local.json`）に `"auto": {"enabled": true}` を書くこと、自動にしないなら今のスキル（task-start から）で進められることを伝える。task-start など、ほかのスキルを代わりに始めない
- `no_hold`：何もせずに終える。止まったときに移す保留の列が無いので始めないことと、repo-setup で保留の列を作るよう伝える
- `not_startable`：何もせずに終える。`reasons` を伝える（親の Issue なら、子の Issue を指定して頼み直すよう添える）
- `hold`：上の「止まる」の手順で止まる（`reasons` を止まった理由にする。着手していない）
- `proceed`：続ける

失敗したら（終了コードが 0 でない）、何もせずに、標準エラーの1行のメッセージをそのまま伝えて終える（設定の値の誤りなど）。

`proceed` なら、`settings` の `max_fix_attempts`・`max_new_issues` と、`resume`（前の作業のブランチ。task-auto の手順2）を覚えておく。`issue`（タイトル・本文・type）から、Issue があいまいでないかを判断する（Issue を読み直さない。判定に使った本文と同じものを見るため）。次のどれかなら、止まる（「止まる」の手順。着手していない）。

- 「やること」と「完了条件」が食い違う、または「完了条件」を満たしたかを確かめる方法が分からない
- 何を作るか・どう振る舞うかに、利用者から見て違う結果になる解釈が複数あり、Issue も、Issue が参照する ADR・設計書・リポジトリの決まりも、どれかに決めていない
- 「要検討」「未定」「〜するか決める」のように、人が決めることが残っている

迷うときは止まる（自動で決めた解釈が外れると、作った PR がまるごと無駄になるため）。

### 2. 着手する

task-start の手順に従い、次のように決める（task-auto の手順1で Issue は読んである）。

1. `next-tasks.sh --issue <番号>` で、着手中の Issue との重なりを確かめる。`issue.overlap` が `conflict` でも `unknown` でも着手し、重なる Issue とパス（`unknown` なら、その理由）を「自動で決めたこと」に覚える。確かめられなかったときも着手し、そのことを覚える
2. 本文の「変更するファイル・領域」が「- なし」なら、止まる（ファイルを変えないタスクは PR を出せない。task-start で着手するよう「続けるには」に書く）
3. `task-start.sh` で着手する。ブランチ名を「自動で決めたこと」に覚える
   - `resume` があれば（止まった後に実行し直したとき）、`task-start.sh --issue <番号> --branch "<resume の branch>"` を実行する。名前を作り直さずに、前の作業のブランチとワークツリーを使い回し、前のコミットから続ける（作業役にも、前のコミットがあることを伝える）。前の作業から続けたことを「自動で決めたこと」に覚える
   - `resume` が null なら、ブランチ名の短い説明を Issue のタイトルから英語で考え（task-start 手順5）、`task-start.sh --issue <番号> --slug "<短い説明>"` を実行する
4. task-start 手順6のエラーのうち、「短い説明に英数字がありません」は短い説明を考え直してもう一度実行する。ほかのエラーで止まったら、止まる

以後の作業は、出力の `worktree` の中で行う（Bash では `cd <worktree>` してから作業する）。task-start 手順7の、結果を伝えた後に実装へ続ける動きは、ここでは行わない（実装は次の手順3で作業役に任せる）。

### 3. 実装とテストを作業役に任せる

Agent ツールで、作業役のサブエージェント（`subagent_type` は `general-purpose`）を1つ起動し、実装・テスト・コミットを任せる。プロンプトには次を書く（Issue の本文は全文を入れる）。

```
あなたは作業役です。Issue #<番号> の作業を、ワークツリー <worktree> の中で行います。
ユーザーには質問できません。AskUserQuestion は使いません。決められないことは、作業を止めて報告に書きます。

Issue #<番号>: <タイトル>（type: <type>）
<Issue の本文の全文>

決まり:
- 作業はすべて <worktree> の中で行う（Bash では最初に cd <worktree> する）。ほかのディレクトリのファイルを変えない
- リポジトリの CLAUDE.md・CONTRIBUTING.md などの開発の決まり（書き方・テストのルール）を読んで従う
- 「やること」の項目を実装し、「完了条件」を満たす。Issue の範囲の外の変更をしない
- 実装に、Issue に書かれていない設計上の判断（他の案と比べて選ぶ・破壊的変更・元に戻しにくい）が要るなら、作業を止めて報告する。Issue の「やること」に ADR を残す項目があれば、その判断は Issue で決まっているので、/dev-workflow:adr-create で ADR を書く
- type が fix なら、同じ原因の他の箇所を、同じ書き方・同じ前提でリポジトリを検索して探し、見つかった分も直して、テストを足す
- スクリプトや振る舞いを変えたら、それを確かめるテストを足す
- リポジトリのテストとチェック（開発の決まりに書かれたもの。無ければ、リポジトリにあるテストの実行方法）を実行して、通ることを確かめる
- 論理的な区切り（1つの変更を仕上げてテストが通ったところ）ごとに、/dev-workflow:commit でコミットする
- push・PR の作成・Issue や PR への書き込みなど、GitHub に書き込む操作をしない。gh は読むだけに使う

報告:
終えたら、次を返す。
- status: done（終えた）・blocked（決められないことがあって止めた）・failing（テストやチェックが通らない）のどれか
- commits: 作ったコミット（短い sha と1行目）
- checks: 実行したテストとチェックのコマンドと、その結果（件数・失敗したもの）
- decisions: Issue に書かれておらず、自分で決めたこと（解釈・直し方の選択など）と理由
- questions: blocked のとき、決められなかったことと、考えられる選択肢
```

報告を受けたら、うのみにせず、次を自分で確かめる。

- `git -C <worktree> status` で、コミットしていない変更が無いこと
- `<worktree>` の中で `merge-target.sh` を実行し、`git -C <worktree> log --oneline --no-show-signature <ref>..HEAD`（`<ref>` は出力の `ref`。前の作業のブランチを使い回して、その PR が設定の `base_branch` と違うブランチに向いていれば、そのマージ先）で、コミットがあること。出力の `fallback` が null でなければ（PR のマージ先をそのまま使えなかった）、標準エラーの警告と、どのマージ先で確かめたかを「自動で決めたこと」に書く
- 報告の `checks` のコマンドを、自分でもワークツリーで実行して、通ること

報告ごとに、次のように進める。作業役に頼み直すときは、SendMessage で同じ作業役に送る（文脈を引き継ぐため）。

- `done` で、確かめたテストとチェックが通る：`decisions` を「自動で決めたこと」に覚えて、task-auto の手順4へ進む
- テストやチェックが通らない（`failing`、または自分で実行して落ちた）：落ちたコマンドと出力の要点を作業役に送り、直させる。直させた回数を数え、`max_fix_attempts` 回直させても通らなければ、止まる
- `blocked`：`questions` に、Issue・周りのコード・リポジトリの決まりから答えられるものがあれば、答えと根拠を送って続けさせ、答えを「自動で決めたこと」に覚える。答えられないものが1つでもあれば、止まる（`questions` を止まった理由にする）
- コミットしていない変更がある、コミットが無い：作業役にコミットさせる（直させた回数には数えない）

### 4. レビューする

`/dev-workflow:review`（Skill ツールの `review`）を実行し、その手順をたどる。確認の代わりに、上の「確認の代わりに決めること」のとおりに決める。

- review の手順5（反映するものを選ぶ）：一覧の各指摘を、Issue の範囲内か範囲外かに分ける。範囲内の指摘はすべて反映する。次は範囲外として反映せず、手順5で起票する候補にする（task-auto の手順5）
  - Issue の「やること」「完了条件」にない変更を求める指摘（ほかの機能への移し替え・Issue の範囲を広げる改善）
  - この差分より前からある不具合（差分が作ったものではないもの）
  - ただし、水平展開（同じ誤りの他の場所）は、指摘を反映するときに一緒に直すので、範囲内に入れる
- review の手順6（反映する）：直しは作業役に任せる（task-auto の手順3と同じ作業役に SendMessage で、直す指摘・場所・直し方を送る。報告は task-auto の手順3と同じに確かめる）。テストが通らなければ、手順3と同じく直させ、回数は task-auto の手順3から通して数える
- review の手順8：上限の周（`review.max_rounds`）でも範囲内の指摘が出たら、その指摘を反映してコミットし（テストが通らなければ、review の手順6の行と同じく、task-auto の手順3から通して数えて直させる）、もう1周せずに手順5・6へ進む。止まらない。最後の反映（コミットと指摘）はレビューされていないので、「自動で決めたこと」に「上限の周の反映（未レビュー）」として覚える。上限より前の周は、スキルの手順どおりに再レビューする
- review の手順9：行わない
- 反映した指摘（番号・要約・コミット）と、反映しなかった指摘（要約と理由）を「自動で決めたこと」に覚える

レビューの指摘で、差分が破壊的変更（既存の利用者が設定やコマンドを直さないと動かなくなる変更）だと分かったら、止まる（`auto-check.sh` は Issue のラベルしか見ないため）。

### 5. 範囲外の指摘を起票する

**範囲外の指摘の内訳**：起票を始める前に、task-auto の手順4のレビューのすべての周の一覧から、範囲外とした指摘（同じ指摘は1件と数える）の数と、1件ずつの要約（ファイルと行）を「自動で決めたこと」に書き出す。その後、下の起票の手順で、書き出した指摘を1件ずつ、次のどれか1つに分けて覚える。分けられない指摘は、起票し忘れたもの

- 起票した（起票した Issue の番号）：`filed`
- 重複していたので起票しなかった（既にある Issue の番号）：`duplicate`
- 破壊的変更になるので起票しなかった：`breaking`
- 上限で起票しなかった：`limit`
- 起票に失敗した：`failed`

**範囲外の指摘の記録**：書き出した指摘と、その分け方を、ワークツリーの外のファイル `${TMPDIR:-/tmp}/task-auto-<実行の id>-findings.json` に残す（実行の id は手順1で決めたもの。Write ツールで書いてよい）。形は `auto-findings.sh --help` のとおりで、指摘ごとに `summary`（ファイルと行を含む要約）・`disposition`（上の `filed` など）・`issue`（`filed` と `duplicate` で、Issue の番号）・`reason`（`breaking`・`limit`・`failed` で、起票しなかった理由）を書く。範囲外の指摘が1件も無ければ `[]` を書く（ファイルが無いことを、指摘が無いことと取り違えないため）。書き出したときは、全件を `summary` だけで足し、起票するたびに、その指摘の `disposition` と `issue` か `reason` を埋める。埋めていない指摘は、手順6の最初の検査で止まる

**内訳が合う**とは、手順4のレビューのすべての周の一覧から、範囲外とした指摘（同じ指摘は1件）を数え直した数と、上で分けた数の合計が同じであること。1周目で範囲外とした指摘が、後の周の一覧には出ないことがあるので、最後の周の一覧だけでは数えない。手順6・7は、この書き出しや覚えた記録の数ではなく、レビューの一覧から数え直して確かめる（書き出しや起票を飛ばしたときに、空の記録どうしで合ったことにしないため）。

書き出した指摘ごとに、task-create の手順に従って、次のように起票する。

1. 開いている Issue を読み（`gh issue list --state open --limit 1000 --json number,title,labels`）、同じ内容の Issue があるかを探す（タイトルで判断できないものは本文も読む）。あれば起票せず、その番号を「自動で決めたこと」に覚える
2. 無ければ、task-create の「下書きの項目」のとおりに下書きする。本文の「背景」には、元の Issue（`#<番号>`）の自動のレビューで見つかった指摘であることと、指摘の中身（ファイルと行・要約・直し方）を書く。Story Point・親・依存は付けない（見積もりと置き場所は人が決める）。破壊的変更になる指摘は起票せず、「自動で決めたこと」に書くだけにする
3. `issue-create.sh --title … --type … --body-file <ファイル>` で起票する。起票した番号と URL を「自動で決めたこと」に覚える。task-create の手順6（着手するかを聞く）は行わず、起票した Issue に着手しない
4. 起票した数が `max_new_issues` に達したら、残りの指摘は起票せず、「自動で決めたこと」に「起票しなかった指摘（上限）」として要約を覚える

起票に失敗したら、止まらずに、失敗したことと指摘の要約を「自動で決めたこと」に覚えて続ける（PR の作成は妨げない）。

### 6. PR を作る

まず、範囲外の指摘の記録を検査する。手順4のレビューのすべての周の一覧から、範囲外とした指摘（同じ指摘は1件）を数え直し、その数を `--expect` に渡す（記録の件数ではなく、一覧から数え直した数にする。記録に書き出し忘れた指摘を見つけるため）。

```bash
${CLAUDE_PLUGIN_ROOT}/scripts/auto-findings.sh --file "${TMPDIR:-/tmp}/task-auto-<実行の id>-findings.json" --expect <数え直した数>
```

止まったら（終了コードが 2）、PR を作らずに手順5に戻る。標準エラーの1行が、起票した番号も理由も無い指摘か、件数の食い違いを示す。書き出し忘れた指摘を記録に足し、起票していない指摘を起票して記録を埋めてから、もう一度検査する。検査が通るまで、次へ進まない。通ったら、出力の `filed`・`duplicates`・`counts` を、本文の「起票した Issue」の元にする。

pr-create の手順1〜4に従い、次のように決める。

- pr-create の手順2の ADR：`adr-list.sh --issue <番号>` の `proposal` が `pending` なら止まる。`judge` なら、差分（と Issue）から「ADR にすべき判断」に当たる判断を探し、あれば止まる（Issue で決まっていない設計上の判断を、自動で決めないため）。迷うときは止まる。`adr-list.sh` が止まったら、そのことを「自動で決めたこと」に覚えて続ける。`--add-task` は付けない
- pr-create の手順3の本文：テンプレートの見出しに沿って書き、`Closes #<番号>` の前に「自動で決めたこと」の節（見出しは本文の見出しと同じ大きさ。`language` が ja でなければ、その言語に訳す）を足す。節には、覚えた内容を項目ごとに書く。無かった項目も「なし」と書く（決めなかったことが分かるように）
  - この PR は task-auto が自動で作ったこと（draft にせず、レビューできる状態で出していること）
  - ブランチ名
  - 着手中の Issue との重なり（重なる Issue とパス、または「重ならない」「分からない（理由）」）
  - 作業役が自分で決めたことと、作業役の問いへの答え
  - テストやチェックを直させた回数
  - 反映したレビューの指摘と、反映しなかった指摘とその理由
  - 上限の周の反映（未レビュー）：上限の周で出た指摘を反映したときは、そのコミットと指摘を書く。最後の反映はレビューされていないので、人や PR のレビューで見てもらう。無ければ「なし」
  - 起票した Issue：手順5の「範囲外の指摘の内訳」（範囲外とした指摘の数と、分けたそれぞれの数・番号・要約）
    - 「起票した Issue」を「なし」と書く前に、手順5の「範囲外の指摘の内訳」が合うか（手順5の「内訳が合う」のとおり、手順4のレビューのすべての周の一覧から数え直す）を確かめる。合わなければ（数え直した指摘に、内訳で分けていないものがあれば）、「なし」と書かずに、手順5に戻ってその指摘を起票してから本文を書く（手順を書いてあっても、起票を飛ばして「なし」と書いたことがあったため）
- pr-create の手順4の「やること」のチェック：差分で済んだとはっきり分かる項目だけに `--check` を付ける。済んだかはっきりしない項目は付けず、「自動で決めたこと」に書く

dry-run（`pr-create.sh --issue <番号> --body-file <ファイル> [--check …]... --no-draft --dry-run`）で、エラーにならないことを確かめてから、`--dry-run` を外して実行する（確認は取らない）。必ず `--no-draft` を付ける。

dry-run や実行が止まったら、pr-create 手順5・6のエラーのうち、次だけを直してやり直す。ほかは止まる。

- 「未コミットの変更があります」：作業役にコミットさせてからやり直す
- 「--check の文の項目が Issue #N のチェックリストに1つだけではありません」：出力の `tasks` の `text` をそのまま指定し直す。決まらない項目はチェックを付けない
- 「PR #N は作りましたが、Issue #N の列を移せませんでした」「PR #N はできていますが、Issue #N のチェックリストを変えられませんでした」：pr-create 手順6のとおりに続きを行う（確認は取らない）

そのブランチの開いた PR が既にあったとき（`created: false`。前に止まった作業の続きなど）は、push とチェックだけが行われ、書いた本文は反映されず、下書きかどうかも変わらない。そのことを結果で伝える（本文も下書きかどうかも直さない）。出力の `draft` が true なら、その PR は前の版の task-auto や人が下書きにしたものなので、下書きのまま残す。`gh pr ready` は実行しない（下書きにしたのが人なら、その意図を自動で覆さないため。ready にするかは人が決める）。手順7で、人に ready にするよう伝える

### 7. 結果を伝える

PR の番号と URL（`pr.url`）、下書きか（出力の `draft`。新しく作った PR は下書きではない）、移した列（`status.skipped` が false なら `status.to`）、「自動で決めたこと」の要点（ブランチ名・重なり・反映しなかった指摘・上限の周の未レビューの反映・起票した Issue）を伝える。

- 既にある下書きの PR を使ったとき（`created` が false で `draft` が true）は、下書きのまま残したことと、PR の自動レビューの多くは下書きをレビューしないので、レビューに出すには人が ready にする（`gh pr ready <PR番号>`）よう伝える
- 手順5の「範囲外の指摘の内訳」を伝え、内訳が合うこと（手順5の「内訳が合う」のとおり、手順4のレビューのすべての周の一覧から数え直す）を確かめて伝える。合わなければ、起票し忘れた指摘があるので、手順5に戻って起票し、記録を直して `auto-findings.sh` で検査し直す。起票した Issue と、PR の本文にはその Issue が書かれていないことを伝える（本文は直さない）。
  - その PR を今回の実行が新しく作ったとき（手順6の出力の `created` が true）に限り、起票した Issue を PR にコメントで足す。コメントの本文を一時ファイルに書き（言語は設定の `language` に従う。「自動で決めたこと」の節の「起票した Issue」が実際と違うこと、後から起票した Issue の番号・URL・指摘の要約を書く）、`gh pr comment <PR番号> --body-file <ファイル>`（PR の番号は手順6の出力の `pr.number`）で付ける。既にあった PR（`created` が false。人や前の実行が作ったもの）には、コメントしない。本文は直さない
  - コメントできなかったら、止まらずに、起票した Issue の番号とコメントできなかったことを結果で伝える

マージは人が行うこと、PR に付いた指摘には gh-pr-check で対応できることを添える。ワークツリーは残っているので、マージされたら task-finish で片付けるよう伝える。
