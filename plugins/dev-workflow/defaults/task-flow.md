# タスクの進め方（dev-workflow）

このセッションでは dev-workflow プラグインが有効です。コードやドキュメントを変える作業は、次の流れで進めます。各段階では、括弧の中のスキルを使います（スキルの手順に、確認を取る場面や使うスクリプトが書いてあります）。

1. **Issue から始めます**。作業はすべて Issue に紐付けます。依頼に対応する Issue が無ければ、先に起票します（`/dev-workflow:task-create`）。起票した後に着手するかは使う人が決めるので、依頼で着手まで頼まれていなければ（「起票して着手して」などでなければ）、着手するかを聞いてから手順2に進みます。
2. **着手します**（`/dev-workflow:task-start`）。Claude が今回起票した Issue は、着手まで頼まれていなければ、使う人が着手すると決めてから進めます（ユーザーが既存の Issue に「着手して」と言ったときは、もう一度聞きません）。ブランチとワークツリーができるので、結果を伝えた後は止まらず、そのワークツリーの中で続けて実装に取りかかります（Issue の内容だけでは進め方が決まらないときは、聞いてから進めます）。ワークツリーを作らずに着手したとき（調査など）は、続けて実装には進まず、結果を伝えて終えます。base_branch（既定は main）の上では作業しません。
3. **実装し、論理的な区切りごとにコミットします**（`/dev-workflow:commit`）。全部を直し終えてから1回でコミットするのではなく、1つの変更を仕上げてテストが通ったところでコミットします。Issue の type が fix（不具合を直す）の作業では、同じ原因の他の箇所も、同じ書き方・同じ前提でリポジトリを検索して探し、見つかった分も一緒に直します。
4. **PR を出す前に、ローカルでレビューします**（`/dev-workflow:review`）。反映する指摘はユーザーが選びます。反映でコードの振る舞いが変わったら、再レビューされます（言い換えやコメントだけなら不要です）。同じ場所や同じ種類の指摘が繰り返し出たら、その場所だけを直さず、根本の原因から直します。レビューを終えた後でも、同じ会話でユーザーが、レビューが見落とした変更への指摘を出したときや、今後も要らないという理由で指摘を却下したときは、`/dev-workflow:review` の手順9（観点に残すか確かめる）に従って、レビューの観点に残すか（今後指摘しないようにするか）を尋ねます。
5. **PR を出します**（`/dev-workflow:pr-create`）。マージは人間が行います。PR に指摘・質問・コメントが付いたり CI が失敗したりしたら、`/dev-workflow:gh-pr-check` で対応します（任意です。使わなくてもマージと後片付けに進めます）。
6. **マージされたら後片付けをします**（`/dev-workflow:task-finish`）。ワークツリーとローカルのブランチを削除し、base_branch を最新にします。片付けを実際に終え、かつ、この会話で、その Issue の task-start や実装・レビュー・PR の作業をしていたときだけ、次のタスクに着手する前に `/clear` するよう勧めます（実行はユーザーが行います。`/clear` の後も、この流れは読み込み直されます。止まったときや、会話にそれが無いときは勧めません）。

- Issue をやめることにしたとき（重複・不要・誤って起票した）は、取りやめます（`/dev-workflow:task-cancel`）。マージした後の片付けには使いません。取りやめを実際に行い、かつ、この会話で、その Issue の task-start や実装・レビュー・PR の作業をしていたときだけ、次のタスクに着手する前に `/clear` するよう勧めます（会話にそれが無いときや、取りやめなかったときは勧めません）。
- Issue を、確認なしで PR まで自動で進めるよう頼まれたときは、`/dev-workflow:task-auto` を使います。設定 `auto.enabled` で有効にしたリポジトリでだけ動き、上の流れの確認に代わりに答えて進めます（無効なら何もしません。上の流れで進めるかは、使う人が決めます）。決めきれないときは、理由を Issue にコメントして保留の列に移して止まります。
- マージされた PR の後片付けから、次の Issue を `task-auto` で PR まで進めるまでを確認なしで続けるよう頼まれたときは、`/dev-workflow:task-auto-sequence` を使います。設定 `auto.enabled`・`auto.merge.enabled`・`auto.chain.enabled` をすべて有効にしたリポジトリでだけ動き、件数の上限（`auto.chain.max`）と止める手段（設定を false にする・PR のラベル `no-auto-merge`）で止まります。
- 次にどの Issue に着手するか、同時に進められるものはあるかを知りたいときは、`/dev-workflow:task-next` を使います（読むだけで、何も変えません）。
- Issue を任意の列（Blocked など）へ移すときは、`/dev-workflow:task-status` を使います。
- 質問への回答や調査だけで、ファイルを変えない依頼には、この流れ（番号の付いた段階）は要りません。
- Issue の分け方や作業の構成（何本に分けるか・親子にするか）を提案するときは、起票の前の相談（ファイルを変えない段階）でも、自分で案を作らずに `/dev-workflow:task-create` を呼び、その下書きとして提案します。task-create は、承認を得るまで起票しません。
- Issue にしたタスクでも、リポジトリのファイルを変えないもの（調査・洗い出し・Issue の整理など）は、`/dev-workflow:task-start` でワークツリーとブランチを作らずに着手できます（割り当てと列の移動だけを行います）。結果は Issue のコメントや別の Issue に残し、終わったら `/dev-workflow:task-finish` で Issue を閉じます（PR が無いので、3〜5 は要りません）。途中でファイルを変えることになったら、もう一度 `/dev-workflow:task-start` でワークツリーを作ってから変えます。
- スキルの外でも（作業の途中で、どう進めるか・どの方法で確かめるかを聞くときなど）、ファイルを変えない依頼（質問への回答・調査）でも、開発者に答えを選んでもらう質問や確認は、文章に並べた平文ではなく、AskUserQuestion で出します。
  - 対象は、選択肢から選んで答えられるものすべてです（「push してよいですか」のような、はい・いいえの確認も含みます）。確認を取るかどうかの線引きは変えません（聞くと決めた確認を、平文ではなく AskUserQuestion で出すということです）。選択肢の無い問い（新しい名前を何にするか、など）は、平文で聞いてかまいません。AskUserQuestion を使えない実行（`claude -p` など）には、この項は当てはまりません。
  - 選択肢の説明には、選ぶと実際に何が起きるか（作るもの・変えるもの・削除するもの・GitHub に書き込むもの）を書き、フラグやスクリプト名といった内部の手順で済ませません。選択肢がコマンドや確かめ方そのもののときは、それを書いてかまいません。
  - 確認に必要な内容（比べる案・判断の理由・下書き）は、質問の前の文章で見せるだけでなく、質問の中（質問の文や選択肢の preview。複数選択の質問では preview を使えないので、選択肢の説明）にも入れます。`/remote-control` で別の端末から使うと、質問の直前の文章が見えないことがあるためです。
- PR・Issue・CI に触れるときは、URL を添えます。git の操作の後のリンクはフックが出しますが、CI やレビューの結果を伝えるとき、Issue を起票したとき、PR や Issue の状態を答えるときなど、フックで出せない場面では、自分で URL を書きます。
